Layer 0no tech

The one-minute version

Chess Arena is a website where two people play chess against each other, live. You make an account, press Play Now, and the site pairs you with whoever else is waiting. Each of you sees the board from your own side. When one of you moves, the other sees it a moment later.

When a game ends, it's saved. You can open My Games later and replay any game move by move.

It lives at chess.bhargavnkrishna.site. Behind it are two programs you wrote (a website and a server) and a database that remembers everything.

The short version

Two players, one live board, and every game is saved so you can replay it later.

Layer 2very light tech

The pieces

Four parts make the app work. A restaurant is a handy way to picture them.

PartIn the restaurantWhat it really is
The browser app
(the frontend)		The dining room and the menu. Everything you see and touch.A React app written in TypeScript. It draws the board, the pages and the buttons inside your browser.
The server
(the backend)		The kitchen. It does the real work and makes the decisions.A program written in Go. It pairs players, checks every move, passes moves along and saves everything.
The databaseThe pantry and the order book. Permanent memory.A Postgres database hosted by Neon. It stores users, games and every move.
The hostThe building the restaurant is in.Render. It runs the server on the internet at your domain.

One detail makes your setup simpler than most: on Render, the browser app and the server live in the same box. The Go server has two jobs. First it hands out the website's files, then it answers the API calls that the website makes. So there's one thing to deploy, one address, and no separate frontend host.

Opening the site happens in two steps:

  1. Getting the app. Your browser asks for chess.bhargavnkrishna.site. The Go server reads the built React files (index.html, plus the JavaScript and CSS) from frontend/dist and sends them. At this point no API call has happened. The browser is just downloading the app.
  2. Using the app. The React app now runs in your browser and starts talking to the same Go server: API calls to /api/…, and the WebSocket at /api/ws.

On your laptop it's different. There, the Vite dev server hands out the React files, and the Go server only answers /api. If that's the picture you had in mind, it's right for local development but not for the live site. Layer 8 compares the two side by side.

Who's responsible for what

  • The browser app draws the board, only lets you drag pieces to legal squares, shows the status line, and remembers which color you are.
  • The server keeps the waiting line, pairs players, checks that every move is legal and that it's your turn, passes moves to your opponent, and saves everything.
  • The database holds three things: users, games and moves.
Key idea · the server is the referee

Both the browser app and the server know the rules of chess. The browser uses them for convenience, so you can't drag a knight in a straight line. The server's check is the one that counts. If someone tampered with their browser to send a cheating move, the server would refuse it.

Key idea · two kinds of memory

The server keeps some things in its own short-term memory (fast, but forgotten when it restarts) and some in the database (slower, but permanent). Knowing which is which explains most of the app's behavior. Layer 5 has the full list.

The short version

A React app in your browser, a Go server that acts as the referee, a Neon database for permanent memory, and Render running the server, which also hands out the website.

Layer 3light tech

How the pieces talk

The browser and the server talk in two different ways. You also need to know how the server knows who you are.

Two ways to talk

HTTP is like sending a letter. The browser asks a question, the server sends one reply, and that conversation is over. It's used for things you ask for: sign up, log in, "who am I?", "put me in the waiting line", "show me my games".

WebSocket is like a phone call that stays open. Once connected, either side can talk at any moment. It's used for things that happen to you: "your opponent moved", "you've been matched", "game over".

Why both? With HTTP, the server can only answer. It can't call you. But when your opponent moves, nobody on your side asked a question. The server needs to speak first, and only the open phone line allows that.

Each player has two phone lines

  • The lobby line is open the whole time you're logged in, on any page. It exists for one message: "you've been matched, here's your game".
  • The game line opens when you're on a game page. It carries moves, resignations and "game over" for that one game.

Both lines go to the same address on the server (/api/ws). The first thing the browser says on a new line tells the server which kind it is.

The wristband: how the server knows it's you

Think of a festival wristband. When you log in, the server gives your browser a signed pass called a JWT, stored in a cookie. It says "this is user 4f2a…, username krishna, valid until tomorrow", plus a signature only the server can make.

  • Your browser shows the wristband automatically with every request, and when it opens a phone line.
  • The server checks the signature. If it's valid, the server knows who you are without looking anything up.
  • The cookie is HttpOnly: JavaScript on the page can't read it, so a malicious script can't steal it.
  • It expires after 24 hours. Then you log in again.
Key idea · never trust what the browser says about itself

The server never believes a message that says "I am player X". It only believes the wristband. That's why one player can't send moves pretending to be the other.

One address for everything

The website, the API (/api/…) and the phone lines (/api/ws) all live at chess.bhargavnkrishna.site. Because everything is on one domain, the cookie just works everywhere, and there's none of the cross-site setup (CORS) that sites with separate frontend and backend addresses need.

The short version

HTTP for asking (letter and reply), WebSocket for being told (open phone line). Each player has a lobby line and a game line. A signed cookie, the wristband, proves who you are on every request.

Layer 4medium

Each feature, step by step

The features from Layer 1 again, now as short stories of what happens behind the scenes. Still no code.

Signing up and logging in

  1. You type a username and password. The browser sends them to the server (POST /api/auth/register).
  2. The server checks the name isn't taken. It scrambles the password with bcrypt and stores only the scrambled version, never the real password.
  3. The server creates your wristband (the JWT, valid 24 hours) and puts it in a cookie in its reply.
  4. The browser now knows you're logged in and shows your name in the top bar.

Logging in is the same, except in step 2 the server scrambles the password you typed and checks it matches the stored one.

Too many attempts? To slow down password guessing, the server allows 5 quick tries, then one every 2 seconds, per internet address. Too fast and you get "too many requests". (Whether this works properly on Render still needs checking: see Layer 10.)

Coming back the next day: when the site loads, the app asks the server "who am I?" (GET /api/auth/me). Valid wristband: you're in. Expired: you're sent to the login page.

Finding a match

Say Alice presses Play Now first, then Bob.

  1. Alice asks to join. Nobody is waiting, so she goes into the line and gets the reply "waiting". Her request is now finished.
  2. Bob asks to join. Alice is waiting, so the server takes her out of the line and pairs them.
  3. The server creates a new game, randomly decides who's white, and saves both players and colors to the database.
  4. Alice's request was answered long ago, so the only way to reach her now is her lobby line. The server sends her match_found with her color.
  5. Bob is still waiting for his reply, so he gets "matched" plus his color right in it. (He's also sent a match_found on his lobby line. Whichever arrives first moves him along.)
  6. Both browsers save their color for this game and open /play/<gameId>.

What if Alice's lobby line happens to be down right then? The server puts the message aside (a "pending" message) and delivers it the moment she reconnects.

Making a move

This is the heart of the app.

  1. You drag a piece. The board only lets you drop it on a legal square, because the browser app knows the rules too.
  2. Your board shows the move immediately, without waiting for the server. This is called an "optimistic" update and it's what makes the game feel instant.
  3. The browser sends the move over your game line: {"type":"move", … "move":"e4", "from":"e2", "to":"e4"}.
  4. The server plays referee: are you one of the two players? Is it your turn? Is the move legal in the current position?
  5. If it's all fine, the server saves the move to the database and updates its copy of the board.
  6. The server forwards the move to your opponent's game line, and their board updates.
  7. If that move ended the game (checkmate, for example), the server also sends "game over" to both of you.

If any check in step 4 fails, the server quietly ignores the move. It doesn't tell you, which is one of the rough edges in Layer 10.

Game over

  • By the board: after every move, the server's chess library looks at the position. Checkmate, stalemate and certain draws end the game automatically.
  • By resigning: you press Resign and confirm. The browser sends {"type":"resign"}. The server records that you resigned, so your opponent wins.
  • Either way the server marks the game finished in the database and sends game_over with the winner (white, black or draw) to both players.
  • Each browser compares the winner with its own color and shows "You won", "You lost" or "Draw" on top of the board.

When your Wi-Fi drops

  1. The browser notices the game line closed.
  2. It tries to reconnect after 0.5 seconds, then 1, 2, 4, 8… up to 30 seconds between tries. Doubling the wait is called exponential backoff, and it stops thousands of browsers from hammering a struggling server at once.
  3. When the line is back, the browser introduces itself again ("I'm here for game X").
  4. It then asks for the whole game over HTTP and compares: "the server has 14 moves, I have 12". It plays the 2 missing moves on its board.

Refreshing the page works the same way: your board starts empty and catches up from the server in one go.

When the server goes to sleep or restarts

On Render's free plan the server shuts down after about 15 minutes with no visitors, and the next visitor wakes it up. The same thing happens on every new deploy.

How an unfinished game comes back: the first time anyone touches that game after a restart, the server reads its moves from the database and replays them on a fresh board, in order. It's like setting up a board again from a written scoresheet. Then play simply continues.

My Games and Replay

  • My Games asks the server for your games (GET /api/games). The server looks up every game where you were one of the players, adds your opponent's name, and sorts newest first.
  • Replay fetches one game with all its moves (GET /api/games/<id>). To show move 17, the browser starts from the opening position and plays moves 1 to 17. Buttons and arrow keys just change that number.

Replay needs nothing special from the server. A replay is just the saved list of moves, played back.

The short version

Login scrambles your password and hands you a wristband. Matchmaking reaches the first player over the lobby line and the second in the HTTP reply. A move shows on your board instantly, gets checked and saved by the server, then forwarded. Disconnects retry with growing waits and then catch up. Restarts lose only short-term things, and games are rebuilt from saved moves.

The server is one Go program in backend/. It's split into folders called packages, and each one has a single job. Think of them as departments in a building.

When GameManager has forgotten a game after a restart, the ws code falls back to asking the store, which reads the players and colors from Neon. That's why games keep working after the server wakes up.

Key idea · why there are locks everywhere

Go handles every connection in its own goroutine, a lightweight thread. Two players can touch the same game at the same instant. A mutex (sync.Mutex) makes them take turns, so the board, queue and switchboard never get half-updated. You'll see mu.Lock() in almost every package.

Key idea · why the store is an interface

The handlers only know "there is something that can create games, apply moves…". They don't know or care whether it's memory or Postgres. main.go picks one at startup based on whether DATABASE_URL is set, and nothing else has to change.

The short version

main.go builds everything. Requests come in through handlers (HTTP), ws (live lines) and auth. matchmaking and game hold the logic, and store saves to Neon. Permanent things are in Neon. The queue, connections and lookups are in memory.

The always-on helpers

React has a feature called context for sharing things with every page without passing them down by hand.

  • AuthContext holds the logged-in user and creates one shared api client (axios pointed at /api, with cookies switched on). When the site loads, it calls /auth/me to restore your session. It also provides login(), register() and logout().
  • WSContext opens the lobby line as soon as you're logged in. When match_found arrives, it saves your color and navigates to the game.
  • ProtectedRoute wraps the private pages. While the session check is running it shows nothing. If you're not logged in, it sends you to /login.

The game page, piece by piece

  • useChessGame (a hook) keeps a chess.js game and gives the page the position (FEN), the move list, a status sentence ("White to move", "Checkmate — Black wins"), and functions like move().
  • ChessBoard wraps chessground, the draggable board from lichess. It's given the position, the legal destination squares for every piece (buildDests), and which color you're allowed to move.
  • Play ties it together:
    • Opens the game line with ReconnectingWebSocket. Every time it connects, it sends auth with the game ID, then calls resync() to catch up.
    • On an incoming move, it applies it. On game_over, it shows the result overlay.
    • When you move: if it's a pawn reaching the last row, it shows the promotion picker first. Then sendMove() applies the move locally and sends it.
    • Resign asks you to confirm, then sends resign.
    • Your color comes from localStorage (color_<gameId>), saved during matchmaking. It decides which way the board faces.
  • GameInfo and GameControls show the status, move list and position, plus the buttons.
  • lib/reconnectingWebSocket.ts is the retry-with-backoff wrapper from Layer 4. lib/wsUrl.ts builds wss://your-site/api/ws on HTTPS and ws://… on plain HTTP, so it works locally and live with no settings.
Key idea · useRef versus useState

The chess.js game object is changed in place, so it lives in a useRef (a box React doesn't watch). After every move, the hook copies the new FEN, move list and status into useState, and changing state is what makes React redraw the page.

The short version

Six pages inside two always-on helpers: Auth (who you are) and WS (the lobby line). The game page combines a chess.js hook, a chessground board and a reconnecting game line that catches up on every connect.

Layer 7medium–deep

The data

What's stored, what's sent, and what every message looks like. Keep this layer open as a reference while reading code.

The three tables

  • Player A is whoever joined the queue first, player B second. Colors are picked randomly, so A isn't always white.
  • current_fen is a snapshot of the board after the latest move, updated on every move.
  • ply numbers each half-move from 0. Ply 0 is white's first move, ply 1 black's reply, and so on.
  • The tables are created by backend/internal/db/migrations/001_create_users.sql, 002_create_games.sql and 003_create_moves.sql.

WebSocket messages

Every message has the same envelope: a type, usually a gameId, and a payload.

DirectionTypeExample
browser → serverauth (lobby){"type":"auth","payload":{}}
browser → serverauth (game){"type":"auth","payload":{"gameId":"9b1c…"}}

The short version

Three tables: users, games (pointing at two users) and moves (pointing at a game). Moves travel as SAN. Boards are stored as FEN. About ten HTTP endpoints, plus four message types going up the line and three coming down.

Layer 8medium–deep

How it's deployed

How your code gets from GitHub to chess.bhargavnkrishna.site, what settings it needs, and why some files in the repo aren't used.

The Dockerfile's three stages

A Dockerfile is a recipe for building a container image. Yours has three stages, and only the result of the last one is kept:

  1. node:20-alpine installs the frontend's packages and runs npm run build. Out come plain files in frontend/dist.
  2. golang:1.25-alpine compiles the backend into a single program, chess-server. CGO_ENABLED=0 makes it fully self-contained.
  3. alpine:latest is a tiny final image. It copies in just the program and the dist folder, then runs /app/chess-server.

When it starts, the Go server sends /api/… to the API, /healthz to the health check, and everything else to the website files. Unknown paths like /play/abc get index.html, so React can show the right page after a refresh.

What the free plans mean

  • Render free: after about 15 minutes with no visitors, the server is stopped. The next visitor waits while it starts again, "50 seconds or more" according to your dashboard banner. Layer 4 covers what's lost.
  • Neon free: the database also pauses when idle and wakes on the first query, which adds a little delay to that first request.
  • /healthz pings the database too, so it tells you whether both are awake and connected.

2 · Checking the wristband

backend/internal/auth/middleware.go

func Middleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        claims, err := TokenFromRequest(r)       // read cookie, verify signature + expiry
        if err != nil {
            http.Error(w, "unauthorized", http.StatusUnauthorized)
            return
        }
        ctx := context.WithValue(r.Context(), UserIDKey, claims.UserID)
        ctx = context.WithValue(ctx, UsernameKey, claims.Username)
        next.ServeHTTP(w, r.WithContext(ctx))    // hand over, with your ID attached
    })
}
  • This is the middleware pattern: a handler that wraps another handler. In main.go you'll see auth.Middleware(http.HandlerFunc(api.ListGames)).
  • Later code calls auth.UserIDFromContext(r.Context()) to get your ID. It never comes from the request body.

3 · Matchmaking

backend/internal/matchmaking/queue.go

func (q *Queue) JoinQueue(playerID string) *MatchResult {
    q.mu.Lock()
    defer q.mu.Unlock()
    if slices.Contains(q.waiting, playerID) {
        return nil                               // already waiting
    }
    if len(q.waiting) > 0 {
        playerA := q.waiting[0]                  // first in line
        q.waiting = q.waiting[1:]
        return &MatchResult{PlayerA: playerA, PlayerB: playerID}
    }
    q.waiting = append(q.waiting, playerID)
    return nil
}

6 · The switchboard

backend/internal/ws/hub.go

func (h *Hub) register(key string, conn *websocket.Conn) {
    h.mu.Lock()
    defer h.mu.Unlock()
    if old, ok := h.clients[key]; ok {
        _ = old.Close()                    // same key again: kick the old line
    }
    h.clients[key] = conn
    if msg, ok := h.pending[key]; ok {     // anything waiting for you?
        _ = conn.WriteJSON(msg)
        delete(h.pending, key)
    }
}

func (h *Hub) sendTo(key string, msg Message) error {
    h.mu.Lock()
    conn, ok := h.clients[key]
    h.mu.Unlock()
    if ok {
        if err := conn.WriteJSON(msg); err != nil {   // write happens outside the lock
            // … forget the conn, keep msg as pending …
        }
        return nil
    }
    h.mu.Lock()
    h.pending[key] = msg                   // not connected: keep it for later
    h.mu.Unlock()
    return errors.New("no-conn, stored pending")
}
  • Keys are playerID for the lobby and playerID:gameID for a game line.
  • Each key holds only one pending message. A second one overwrites the first.
  • Writing outside the lock is the root of a rough edge (Layer 10).

8 · The reconnecting socket

frontend/src/lib/reconnectingWebSocket.ts

this.socket.onopen = () => {
  const wasReconnect = this.hasConnectedBefore;
  this.hasConnectedBefore = true;
  this.attempt = 0;                       // reset the backoff
  this.onOpen(wasReconnect);
};
this.socket.onclose = () => {
  if (this.intentionallyClosed) { this.onClose(); return; }
  this.scheduleReconnect();
};

private scheduleReconnect() {
  const delay = Math.min(this.initialBackoffMs * Math.pow(2, this.attempt), this.maxBackoffMs);
  this.attempt++;                         // 500, 1000, 2000, 4000 … capped at 30000
  this.reconnectTimer = window.setTimeout(() => this.connect(), delay);
}
  • close() sets intentionallyClosed, so leaving a page doesn't trigger reconnect attempts.
  • Messages sent while the line is down are dropped with a warning, not queued.

The short version

Startup picks a store. Middleware attaches your ID. The queue pairs under a lock. The WebSocket handler checks the wristband, then routes lobby or game. A move passes three checks, gets saved, then forwarded. The Hub keeps lines and pending messages. Games rebuild from the moves table. The browser retries with backoff and resyncs every time it connects.

Layer 10deep

Rough edges

Things that aren't quite right yet, worst first. Every real project has a list like this. Each item says what happens, why, and how it could be fixed.

The login limiter may trust a header anyone can fake security · needs checking

What happens
Possibly, someone could make unlimited password guesses by sending a different made-up CF-Connecting-IP header with each request.
Why
clientIP() in auth/ratelimit.go trusts that header first. It was written for the Cloudflare tunnel, where Cloudflare always overwrites it with the real address. On Render it depends on what sits in front of the app. If Cloudflare is in front (your own Cloudflare proxy, or Render's edge if it uses Cloudflare), the header is still trustworthy. If not, it comes straight from whoever sent the request. And without the header, every request may appear to come from Render's own proxy, so all users would share one limit.
Check
Temporarily log clientIP(r), then send a login request with a fake CF-Connecting-IP: 1.2.3.4 header. If the log shows 1.2.3.4, the hole is real.
Fix
Read the client address only from a header your host is guaranteed to set and overwrite.

Two writers on one connection can break a line bug · rare

What happens
If two messages are written to the same WebSocket at the same instant (for example one player resigns exactly as the other moves), gorilla/websocket panics with "concurrent write to websocket connection". Go's HTTP server catches that panic, so the whole server keeps running, but that player's line drops and a message can be lost or garbled. The browser then reconnects and resyncs.
Why
The gorilla/websocket library allows only one writer per connection at a time. Hub.sendTo writes outside its lock, and each player's goroutine can write to the other's connection.
Fix
Give each connection one writer goroutine fed by a channel, or a small mutex per connection that every write takes.

Rejected moves fail silently bug

What happens
If the server refuses a move, your board still shows it and your opponent never receives it. The two boards disagree until you refresh.
Why
Each check in serveGame just does continue. The browser already applied the move optimistically, and resync() only adds missing moves, it never removes extra ones.
Fix
Send a move_rejected message back and have the browser undo the move or reload the game.

Under-promotions turn into queens after a reconnect bug

What happens
Promote to a knight, then refresh or reconnect: your board now shows a queen, while the server correctly has a knight.
Why
resync() calls move(from, to) without the promotion piece, and move() defaults to "q".
Fix
Use the fifth character of the stored uci (e.g. e7e8n), or apply the stored san directly.

The move that's forwarded isn't the move that was checked bug

What happens
A tampered client could send SAN e4 (which passes the check) with from/to of a different move. The opponent's board shows the wrong move.
Why
The server validates payload.move but forwards the original message, and the opponent's browser applies from/to.
Fix
Forward what the server actually applied: the MoveRecord returned by ApplyMove (from, to, uci).

Two tabs keep kicking each other off bug

What happens
Open the site in two tabs of the same browser: their lobby lines take turns disconnecting each other about every half second. The same happens with one game open in two tabs.
Why
Hub.register closes any existing line with the same key. The kicked tab reconnects after 0.5 seconds and kicks the other one back.
Fix
Allow several lines per key (a list instead of one), or tell the old tab "replaced" with a special close code so it stops reconnecting.

Your color is only remembered in one browser bug

What happens
Open a game from another browser or device (or after clearing site data) and the board assumes you're white. If you're actually black, it faces the wrong way, lets you drag white's pieces, and the server rejects those moves.
Why
Play.tsx reads the color from localStorage and defaults to white.
Fix
Work it out from GET /games/:id, which already includes both players' IDs and colors, the way Replay.tsx does.

The waiting line never forgets you limitation

What happens
Press Play Now, then leave. You stay in line. When the next person joins, you're paired with them. If you're still on the site, you get pulled into a game. If you've left, they sit in a game alone.
Why
Queue.LeaveQueue exists but nothing calls it.
Fix
Call it when the matchmaking page closes (a small leave endpoint) or when the lobby line disconnects.

Your screen can say "draw" while the server keeps playing limitation

What happens
On a threefold repetition, the status line says "Draw by repetition", but no game-over message arrives and moves are still accepted.
Why
chess.js in the browser reports threefold repetition. The server's notnil/chess only ends a game by itself on automatic draws (such as fivefold repetition or insufficient material). Threefold is a draw a player has to claim.
Fix
Add a "claim draw" message the server can accept, or have the server treat threefold as final.

Saving a move is two separate writes limitation

What happens
If the second write fails, the game's board snapshot and its move list disagree, and the in-memory board is already a move ahead.
Why
PostgresStore.ApplyMove runs UPDATE games and then INSERT INTO moves without a transaction.
Fix
Wrap both in one transaction. On failure, drop the in-memory session so it's rebuilt from the database.

Smaller things tidy-up

  • Only one pending message per player. A second message overwrites the first. Mostly harmless, because resync() recovers moves.
  • Messages can name a different game than their line. serveGame uses the gameId inside each message rather than the one the line was opened for. You still have to be a player in that game, so it's untidy rather than dangerous.
  • Undo, New Game and Flip Board on the game page. Undo and New Game change only your own board, putting it out of sync. Flip does nothing.
  • Any database error reads as "not found". GetGame returns ErrorNotFound for every error, including a Neon hiccup while it wakes up.
  • GET /games/:id needs no login. Anyone with a game's ID can read it. IDs are random UUIDs, so they're hard to guess. Just make it a deliberate choice.
  • POST /games/:id/move isn't used, doesn't notify the opponent, and returns 404 after a restart because it only checks the in-memory GameManager.
  • initial_fen holds the current position. Rename it to current_fen.
  • No automated tests yet. matchmaking/queue.go and game/session.go are the easiest place to start.
The short version

Check the rate limiter's IP source first (security), then fix the concurrent-write problem. After that, the sync bugs: silent rejections, promotions on resync, forwarding the checked move, tab fights and remembered color. The rest is housekeeping.

Glossary

axios
A JavaScript library for making HTTP requests. The app uses one shared instance called api.
Exponential backoff
Retrying with a wait that doubles each time (0.5s, 1s, 2s…), usually with a cap.
bcrypt
A deliberately slow way to scramble passwords so stolen hashes are hard to crack. You can check a password against it, but you can't unscramble it.
Caddy
A web server often used to route traffic. Your repo has a Caddyfile from the self-hosting attempt. It isn't used on Render.
chessground
The board UI library from lichess. It handles drawing and dragging, but not the rules.
chess.js
A JavaScript chess rules library used in the browser for legal moves and game status.
Container
A packaged, isolated environment holding a program and everything it needs. Render runs yours.
Context (React)
A way to share values (like the logged-in user) with every component below a provider.
Cookie
A small value the browser stores and sends back automatically. HttpOnly means scripts can't read it. Secure means it's only sent over HTTPS. SameSite=Lax limits sending it from other sites.
CORS
Browser rules about one website calling another website's API. Mostly irrelevant here, because everything is on one domain.
Docker / Dockerfile
A tool and a recipe file for building container images.
FEN
Forsyth–Edwards Notation: a one-line description of a chess position.
Frontend / backend
The frontend is the part that runs in your browser. The backend is the part that runs on the server.
Goroutine
Go's lightweight thread. The server runs one per connection, so many games happen at once.
Hook (React)
A function starting with use that gives a component state or behavior, like useChessGame.
HTTP
The request-and-reply protocol of the web. One request, one response.
Interface (Go)
A list of methods. Any type that has those methods fits, which is how MemoryStore and PostgresStore are interchangeable.
JWT
JSON Web Token: a small signed piece of data ("user X, valid until Y"). The server can verify it without a database lookup.
Migration
A numbered SQL file that changes the database structure. Each one runs exactly once.
Mutex
A lock that lets only one goroutine at a time touch some shared data.
Neon
A hosted Postgres service. Your database lives there.
notnil/chess
The Go chess library the server uses as referee.
Postgres
PostgreSQL, a popular SQL database.
React
A JavaScript library for building user interfaces from components.
Render
The hosting service that builds and runs your container at your domain.
SAN
Standard Algebraic Notation, how people write moves: e4, Nf3, O-O.
SPA
Single-page app: one HTML page where JavaScript swaps the content as you navigate, instead of loading new pages.
UCI notation
Moves written as from-square plus to-square: e2e4, e7e8q.
Vite
The frontend build tool and dev server.
WebSocket
A connection that stays open so both sides can send messages at any time.
